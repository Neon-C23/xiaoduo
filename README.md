# 0109 · 自动回复质量评估流水线

## 项目背景

团队上线了"客服自动回复"功能，需要评估回复质量。业务方的要求比较模糊："回复要准确、有用、语气好，不能瞎编"。

本项目将模糊的业务需求转化为可运行的评估方案，实现对自动回复质量的多维度自动化评估。

## 评估指标定义

### 指标选择理由

从业务方的模糊描述中，我们定义了 4 个可自动评估的指标：

| 指标 | 权重 | 量化方式 | 选择理由 |
|---|---|---|---|
| **Accuracy**<br>准确性 | 35% | 0-5 分，基于回复是否正确理解问题并给出准确回答 | 直接对应"准确"，是客服回复的核心要求 |
| **Helpfulness**<br>有用性 | 30% | 0-5 分，基于是否提供解决方案和具体步骤 | 直接对应"有用"，区分"正确但没用"的情况 |
| **Factual Reliability**<br>事实可靠性 | 25% | 0-5 分，检测是否编造政策、流程、时间等具体信息 | 直接对应"不能瞎编"，防止误导用户 |
| **Tone**<br>语气 | 10% | 0-5 分，评估礼貌度、自然性和专业性 | 直接对应"语气好"，提升用户体验 |

### 最终得分计算

```
Final Score = Accuracy × 0.35 + Helpfulness × 0.30 + Factual Reliability × 0.25 + Tone × 0.10
```

### 结果状态定义

- **PASS**: Final Score ≥ 4.0，Accuracy ≥ 3，Factual Reliability ≥ 4
- **WARNING**: 3.0 ≤ Final Score < 4.0，且无 Critical Failure
- **FAIL**: Final Score < 3.0 或存在 Critical Failure
- **Critical Failure**: Accuracy ≤ 1 或 Factual Reliability ≤ 1

## 评估方法

### 评估模式

1. **Mock 模式**（离线规则评估）
   - 基于预定义规则进行评分
   - 无需 API Key，快速运行
   - 适合开发测试和 CI 集成

2. **LLM 模式**（AI 评估）
   - 使用 DeepSeek API 进行语义理解评估
   - 更准确的评分，但需要 API Key
   - 推荐用于生产环境质量评估

3. **无参考答案模式**（生产评估）
   - 仅基于问题和回复进行评估
   - 不依赖人工参考答案
   - 适合大规模实时评估场景

### 评估流程

```
输入数据集 (auto_replies.json)
        ↓
    加载解析
        ↓
    ┌───────┴───────┐
    ↓               ↓
Mock Judge      LLM Judge
    ↓               ↓
    └───────┬───────┘
            ↓
    多维度评分计算
            ↓
    报告生成 (Markdown)
```

### 评估器校验

通过与人工标注数据对比，计算：
- **Agreement Rate**：评估器与人工评分的一致率
- **MAE**：平均绝对误差
- **Critical Failure Recall**：关键失败检测召回率

## 局限性讨论

### 当前评估方法的局限性

1. **参考答案依赖性**
   - 有参考答案模式下，评估准确性受限于人工标注的质量
   - 人工参考答案可能不是唯一正确答案
   - 不同标注者可能有不同判断标准

2. **Factual Reliability 评估困难**
   - 在没有完整知识库的情况下，难以判断信息是否为"编造"
   - 常见的政策声明（如"7天退货"）可能因商品类别而异
   - 无参考答案时，该维度评分更保守

3. **语境理解限制**
   - Mock 模式基于规则，无法理解复杂语境
   - LLM 模式虽然更好，但仍可能受训练数据偏差影响
   - 某些行业特定知识可能无法准确评估

4. **评分标准的主观性**
   - "提供了一定帮助"vs"帮助有限"的界限模糊
   - 语气评分受文化背景和个人偏好影响
   - 准确性和有用性的区分有时依赖具体场景

5. **数据规模限制**
   - 当前 20 条样本仅用于验证方法
   - 小样本量可能无法代表真实业务分布
   - 需要更大规模的数据集来验证评估方法

### 可能评不准的 Case 类型

1. **边界情况**
   - 回复"基本正确"但用户期望更具体
   - 语气礼貌但略显机械
   - 提供了帮助但需要用户进一步操作

2. **复杂场景**
   - 需要跨部门协调的问题
   - 涉及多个政策叠加的情况
   - 需要查询外部系统的场景

3. **主观体验**
   - 用户情绪对语气评价的影响
   - 不同用户对"帮助性"的期望差异
   - 文化背景对礼貌标准的影响

### 改进建议

1. **知识库集成**
   - 接入真实的产品文档和 FAQ
   - 建立政策数据库支持事实核查
   - 完善业务规则库

2. **多评估器集成**
   - 结合规则评估和 LLM 评估
   - 使用多个 LLM 进行投票
   - 引入人工审核机制

3. **持续校准**
   - 定期用新的人工标注校准评估器
   - 根据业务反馈调整权重
   - 建立评估结果的反馈闭环

4. **分场景评估**
   - 按业务类型（退款、咨询、投诉等）分别评估
   - 不同场景使用不同的评估标准
   - 提供场景化的改进建议

```bash

# 无参考答案模式（生产评估）
./reply_eval --mode mock --input ../doc/auto_replies.json --skip-reference
```

### 最差 3 条 Case 分析

#### Case case_03 - FAIL (最终分: 2.50)
- **问题**：用户问退款进度，自动回复给通用说明而非直接查询
- **分析**：回复信息准确但帮助性有限，没有主动帮用户查询实际状态
- **改进建议**：增加"我帮您查一下订单"等主动性表述

#### Case case_04 - FAIL (最终分: 2.90)
- **问题**：用户已明确说才买三天，自动回复仍先给排查步骤
- **分析**：虽然提到质保期，但增加用户操作负担，未直接给出解决方案
- **改进建议**：优先提供直接解决方案（退款/换新），减少用户操作

#### Case case_18 - FAIL (最终分: 2.60)
- **问题**：自动回复罗列可能原因但没有帮用户查实际状态
- **分析**：信息准确但缺乏实际帮助，用户仍需自己排查
- **改进建议**：增加主动查询和直接解决方案

- **评估结论**: ⚠️ 评估器与人工标注一致性中等，建议调优评估规则
